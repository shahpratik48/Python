How Agile Dev Assist works for a whole team on a shared server

Two questions came up: how the tool fits our feature-branch workflow when every developer uses it, and how each developer's sessions, chat history and context are kept apart when it is hosted centrally. This page answers both and lists the decisions still open with the platform team.

Question 1. Developers create a feature branch from a base branch (e.g. ikg-master) named storyid-system-feature such as 2400-ikg-beneficiary-enrichment, commit, then merge it into ikg-dev. Branch names differ per application. How does the tool follow that when everybody uses it?
Question 2. When the tool is hosted on a web / app server and all developers work in it, how are their sessions, chat history and context maintained and separated?

1. The tool follows the team's git flow; it does not replace it

Agile Dev Assist never merges. It does exactly what a developer does by hand today, under that developer's own identity, and stops at the merge request. The gate stays where it is: the MR review and the merge into ikg-dev are done by people.

One story, one feature branch, one merge request. The tool's commits are prefixed agile_dev_assist: and carry the developer's name, so git history shows who generated what.

Where the conventions live

Each system has a prebuilt template that every user sees (IKG, ODM, NLG). A template carries the system's knowledge pack and its git conventions, all in one config block; a new application is one more line, nothing in code.

What happens with many developers

Two developers, two stories

Two branches with different story ids, from the same base. Exactly today's situation; the MRs are reviewed independently.

Two developers, the same story

The branch name is derived from the story id, so the second push finds the branch and adds a commit to it (the tool reports "branch exists, commit added"). If they should work separately, one edits the name in the push form (-v2).

Base branch moved on

The branch is created from the current base at push time, not from when the chat started. Conflicts are therefore rare and, when they happen, are resolved in the MR as today.

Who is accountable

Nothing is pushed with a shared token. The developer types their own GitLab token in the push form; the commit author, the branch and the MR are theirs. The tool has only a read token for cloning.

2. Hosting: one server, many developers, everything kept apart by user

The application is a single Python service. Developers reach it through the corporate SSO gateway, which tells the service who they are. Every chat belongs to one user and lives in that user's own folder; shared material (knowledge packs, cloned repositories, model cache) is read-only and contains no personal data or secrets.

Concurrency and capacity

  • A run is model-bound, not CPU-bound: one service process comfortably runs several chats in parallel; the limit is the Azure OpenAI tokens-per-minute quota, which the client paces itself.
  • Scaling is horizontal: more worker processes or instances behind the gateway with the storage volume shared. Sessions are cookie-based and chats live on disk, so any instance can serve any user. The only per-process state is the memory vault, which the UI re-asks for.
  • Expected footprint for a team of 20–30 developers: one instance (2–4 vCPU, 4–8 GB) plus a few GB of storage; packs and repository clones dominate the disk, not chats.

Security and audit

  • The app port is reachable only through the SSO gateway (header mode) or the app does OIDC itself; either way users are identified by e-mail.
  • Greenplum is opened read-only with a statement timeout and the user's own credentials; git pushes use the user's own token; the service token can only read.
  • Every chat folder is a complete audit trail: inputs, plan, each generated file, validator and reviewer findings, tokens and cost, pushes with branch and MR links.
  • Commit messages and MR titles are prefixed agile_dev_assist:, so generated code is recognisable in git history and can be filtered in reports.
