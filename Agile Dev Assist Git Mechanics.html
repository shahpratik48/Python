Fetch, checkout and push: what actually happens for each developer

The tool keeps two things strictly apart: reading the repository (so the agents know the existing code) and writing a branch (push). Reading uses read-only snapshots; writing uses the GitLab API with the developer's own token. There is no writable working copy on the server, so simultaneous developers cannot step on each other's checkout.

Key fact. The server never runs git checkout on a shared working tree and never runs git push. Reads are shallow read-only clones (or the nightly pack snapshot); writes are three REST calls to GitLab: create branch → commit files → open merge request.

Scenario 1 — Developer starts from the IKG template (knowledge pack)

No git traffic at all during the session. The nightly Airflow job already cloned ikg-dags@develop, analysed it and packed the repository copy into ikg_pack.zip. The server unpacks that zip once per content hash and every chat reads the same folder.

Processes involved: Airflow task (git clone --depth 1 --filter=blob:none --sparse, service read token) → zip; server (zipfile.extractall, BM25/identifier index built once and cached as .agiledev_index.pkl). No git process runs during a chat.

Scenario 2 — Developer adds a live repository (Code repo icon)

Needed when the story targets a branch the pack doesn't cover (ikg-master vs the pack's develop), a repository without a pack, or commits made today. The clone is private to the user and keyed by branch.

Technically: git clone runs as a subprocess under the server account with the token passed through an in-memory credential helper (never written to disk). The checkout under .git_checkout/ is only used to copy files out; the index reads the copies. user2 adding the same repository gets a separate clone under …/user2@ubs.com/…: nobody's re-sync changes what another user is indexed against. Reused for cache_hours (24 h) unless "re-sync" is ticked.

Scenario 3 — Push: feature branch + merge request

Generated files live in the chat folder until the developer presses Push and types their personal token. The server then talks to GitLab's API; it does not use any clone.

Equivalent to the manual sequence git checkout -b 2400-ikg-… ikg-master && git add … && git commit && git push -u origin … + "New merge request", done server-side through the API in one go, authored by the developer. GitLab serialises commits on a branch, so two simultaneous pushes never corrupt it.

Why this holds up with many simultaneous developers

  • No shared mutable git state on the server: packs are immutable per version, live clones are per user, generated files per chat.
  • All writes go through GitLab's API under the developer's identity, so permissions, protected branches and MR approvals apply exactly as for a manual push; the service token cannot push.
  • Branch creation uses the base tip at push time, so the tool never "re-opens" an old state of the base branch.
  • One run per chat at a time; chats and users run in parallel without touching each other's data.
